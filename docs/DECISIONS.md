# Design decisions and trade-offs

Short records of the choices that shaped the system. Each states the decision, the alternatives considered and why.

## 1. Salary history is append-only, with "current" meaning `effective_to IS NULL`
**Alternatives:** a `salary` column on `employees` plus an audit log; or a `current_salary_id` pointer.
**Why:** HR needs "what did we pay this person on date X" and "who changed what, when and why". Modelling each period as a row answers both without a separate audit table, and a partial unique index makes "exactly one current salary" a database guarantee rather than application discipline. The cost is one join to read a current salary; see PERFORMANCE.md for why that is cheap.

## 2. Analytics are computed in SQL on every request, no caching
**Alternatives:** materialised summary tables; a nightly job; caching in Rails.
**Why:** At 10k employees, all seven aggregates take ~4 ms with `percentile_cont`. Caching would add invalidation logic (every salary change) for no visible benefit. If the org grew 100x, the first step would be a materialised view refreshed on salary change, not application caching.

## 3. USD normalisation via an `exchange_rates` table joined at query time
**Alternatives:** store `amount_usd` on each salary record; convert in Ruby.
**Why:** Joining at query time keeps one source of truth for the math (`ExchangeRate::USD_AMOUNT_SQL`) shared by sorting, analytics and export, and means a rate update changes every view consistently. Storing a snapshot would be right if the business wanted "USD at the time of the change"; that is a product question left open and noted in REQUIREMENTS.md. Rates are static and seeded, deliberately: live FX would make results and tests non-deterministic.

## 4. GraphQL with offset pagination instead of Relay cursors
**Alternatives:** Relay connections; REST.
**Why:** The HR manager works with a table that has page numbers and a total count; Relay cursors make both awkward. The data set is bounded (an org, not a feed), so offset paging is correct and simpler. GraphQL itself earns its place through typed, generated client code and the ability to fetch a profile with its history in one round trip. Relay boilerplate generated by graphql-ruby was removed.

## 5. Mutations return `errors: [UserError]` rather than raising
**Why:** Validation failures are expected user input, not exceptions. A typed `{ path, message }` list lets the UI place messages next to fields (including nested ones like `salary.amount`) and keeps HTTP 200 for a well-formed request. Transport and programming errors still surface as GraphQL errors.

## 6. Service objects return a `Result`, controllers and resolvers stay thin
**Why:** `Employees::Create`, `Employees::Update` and `Salaries::Adjust` hold the business rules and are tested directly with no GraphQL involved. Mutations only map arguments and payloads. The same services could back a CSV importer or a CLI later.

## 7. Reference data in code, not tables
**Why:** Departments, levels, countries and reasons change rarely and are needed by validations, seeds and the UI. A constant with validations is simpler than three lookup tables and admin screens, and the ordered level ladder is naturally expressed as an array. If HR needed to self-serve edits, the `filterOptions` query is the single seam to swap.

## 8. Search via a stored generated column with a trigram index
**Alternatives:** `OR`-ed `ILIKE`s on three columns; full-text search.
**Why:** One indexed column keeps the query simple and fast for substring matches on names, emails and codes, which is how HR actually searches. Full-text stemming adds nothing for proper nouns.

## 9. The directory's state lives in the URL
**Why:** Filtered views can be bookmarked and shared, back/forward works, and the CSV export can reproduce exactly what is on screen from the same parameters.

## 10. One deployable unit: Rails serves the built SPA
**Alternatives:** separate static hosting for the web app with CORS.
**Why:** One Dockerfile, one service, no CORS in production, no cross-origin cookie questions when auth is added. Hashed assets are cached for a year; `index.html` is served with `no-store`.

## 11. A small, documented gender pay gap in the seed data
**Why:** The pay-equity chart is one of the most important questions the HR manager asks. Synthetic data with no gap would make the feature look broken. The factor is small (female 0.97, non-binary 0.98) and stated in the generator's source. It is synthetic data and should not be read as a claim about anything real.

## 12. Things deliberately not built
See REQUIREMENTS.md. The biggest are authentication/authorisation, bulk import and total compensation. The code leaves seams for each: a `context` hash in `GraphqlController` for `current_user`, services that an importer would call, and a `salary_records` table that extends to other compensation components.
